---
name: follow-through
description: Maintain the developer-activated Paseo workspace's PR history, remaining obligations, developer-sent repair batches, and archive readiness.
---

Keep routine bookkeeping silent. Never announce tracker calls, say the sidebar was updated/synced, recap its visible state, or add plugin-status commentary/final paragraphs. Put receipts, evidence and sync summaries in the tools. User-facing messages cover actual work outcomes or decisions/blockers requiring the developer. Only discuss sidebar status when explicitly asked. A bookkeeping-only continuation should finish its tool calls without repeating the previous answer or sending a sidebar recap.

Use the follow-through MCP tools when available, or the bridge in `FOLLOW_THROUGH_CLI` with `node "$FOLLOW_THROUGH_CLI" call <tool> '<json>'`. Tracking starts through Track this workspace or a user-enabled project default. The developer sends a batch by clicking its control, or enables Auto for this workspace. Enrollment never enables Auto or sends messages. Polling sends only when this workspace has explicit Auto consent. Use `enroll_workspace` to refine the inferred goal. Never ask the developer to enter a goal, enroll, register PRs or maintain this tracker. Recovery is an optional human action under Workspace → Recovery, available repeatedly. It never gates manually maintained tracking, repairs, deployment tasks or main-agent Done, and Auto never starts recovery. Recovery batches run in a separate agent in the same workspace. Recovery reads an evidence file and updates only tracking metadata, preserves main-agent ownership, never edits code or pushes, and cannot declare Done. Acknowledge its own recovery batch; its metadata access ends after acknowledgment. On an inventory batch, recover all workspace-produced PRs/stacks and unfinished work from the full conversation, earlier compactions, local transcripts and git/Graphite history. Historical candidate URLs are references, not proof of ownership. Read `workspace_status` after compaction and before declaring completion.

Register every PR this workspace produces with `register_pr` after submission. Register parents before children and update parent relationships after a split/reparent. Use meaningful stack names and preserve existing history. A Linear issue is optional. A referenced external PR is not automatically owned by this workspace.

Maintain this sidebar during normal work without a developer reminder. Before ending a normal turn, reconcile the goal, owned PRs, stack relationships and substantive tasks, then call `sync_workspace` with a concise summary, even if no changes were needed. This confirms bookkeeping only; it never declares Done or starts repair/recovery work. The provider hooks restore these instructions at session start, on each prompt and after compaction, and allow one missed-sync continuation. Never transfer ownership or ask the developer to update the sidebar.

Record remaining implementation, decisions, deployment verification, migrations, and other post-merge work using `update_obligation`. Dependencies use `owner/repo#number` keys. Tasks are substantive follow-through, never approve/merge/deploy checklist entries: PRs already track their lifecycle. Use concise action titles, for example "Verify vendor resolution in production", and put dependencies in afterPrs rather than restating the merge steps. Tasks are manual unless explicitly scheduled with trigger={event:"now"|"merge"|"deploy",delayDays:0}. Only set a trigger from the developer’s requested timing; never infer timing from a title or enable_follow_up alone. Merge/deploy triggers require owned afterPrs; delayDays=14 waits fourteen days after the last dependency event. Now requires no PR dependencies or delay. Deployment timing starts at the first verified fully serving observation and remains conservative when history is unknown. Preserve existing trigger fields on updates; trigger=null makes a task manual. Auto controls delivery, not timing or production permissions. Delivery still respects workspace Auto consent and production permissions. A deploy tag or merged PR alone never establishes deployment. Record result evidence for done or waived obligations. Preserve fields while updating; leave an obligation blocked when the developer must act.

Repair, obligation and completion batches contain only a `Follow-through batch <batchId>` header and ordered tasks. Read `workspace_status` and refresh live conditions before acting; skip resolved tasks. Process dependent PRs bottom to top, one PR fully before the next. Use the repository's `/fix-pr` workflow, validate feedback, verify changes, submit through Graphite with `--publish`, and reply/resolve addressed threads. Follow the repository's safe reparent procedure for merged parents and preserve uncommitted work. Do not merge or archive. For post-deploy tasks, verify the currently serving revision contains every dependency and record behavioral results separately from deployment evidence. Call `acknowledge_batch` with the header's batchId and a concise result before ending the turn; use blocked for work requiring a decision. Acknowledge completion batches before declaring Done. Production actions still follow the workspace's existing authorization.

When the whole goal is fulfilled, call `declare_done` with the outcome. Resolve returned blockers first. A merged stack alone is insufficient. Done labels the workspace; the developer archives it. New scope, PRs, or obligations reopen it.

Stakeholder replies belong in follow-through. When the developer asks for an update to a requester, use `update_obligation` with a concise action title and `communication` containing the original Slack `threadUrl`, `recipient`, `purpose` (`progress` or `verified`), and the actual developer `authorization`. Capture these from the conversation; never ask the developer to fill in tracking data. A historical mention or a requester asking for a bug fix is not permission to post as the developer. Empty authorization keeps the task out of delivery even with Auto on. Preserve destination and authorization when updating; pending duplicates for the same thread/recipient/purpose reconcile into one task.

Send the requested progress update using fresh evidence: what is fixed, what is deployed, what has been verified, and the blocker/next step. Read the original thread first and avoid repeating an equivalent existing update. For a final update, record a separate `purpose=verified` task such as "Verify the vendor fix and update the requester", with deployed `afterPrs` dependencies. Deployment alone does not authorize a success claim; verify behavior before replying. Existing production permissions still apply. A communication-only request does not authorize running queued repairs, benchmarks or migrations.

Use the agent's authorized Slack connection to post in that exact thread, then save the actual sent message permalink in `communication.replyUrl`, mark the task done and record result evidence. If an equivalent update already exists, verify and record its permalink instead of posting again. A draft, a read-only connection or an uncertain send remains blocked; record the reason and inspect the thread before retrying. Do not change connector permissions or claim a message was sent. Communication tasks with no reply receipt prevent Done and cannot acknowledge their batch completed. Waive only with explicit decision evidence. The plugin tracks and dispatches these tasks; it does not create a separate Slack posting identity or scan channels in the background.

A developer-confirmed scope exclusion is durable. Use `exclude_stack` with the evidence/reason and related obligation IDs when correcting an unrelated stack. Its records remain in the exclusion audit; do not re-register excluded PRs or stacks from historical mentions. External dependencies are not owned PRs. Recovery handoffs preserve the main owner and require the exact initial user task in a replacement agent after the original recipient is archived. Keep acknowledgment results within 2000 characters.

Use native Follow-through MCP tools first. Their replies contain current work or the exact changed record; workspace_status with detail=full retrieves complete history. Already-running sessions can use the CLI compatibility bridge with --compact, or omit that flag for older full-response scripts. Run the bridge with list to inspect schemas. Unknown argument names are rejected; dependencies are afterPrs with owner/repo#number strings. Ordinary task updates preserve omitted dependencies/evidence/schedule, while completion requires fresh result evidence.

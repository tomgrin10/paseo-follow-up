# Paseo Follow-up: agent guide

Start here. This file tells you where things live, what must stay true, and how to test and ship a change. Each
subsystem has a short doc in [docs/](docs/); the [file index](#file-index) says which doc covers which file.
`tests/docs.test.ts` fails when an RPC, an agent tool or a source file isn't mentioned in AGENTS.md or docs/.
Update the docs in the same PR as the code.

Follow-up is a trusted Paseo plugin (unsandboxed, runs on the daemon host). It follows every workspace's PRs until
the work is done, sends repair batches to each workspace's main agent, shows what needs the developer (Home, the
panel, the pill, the Needs-you inbox), and gives agents tools for everything the developer can click.
[README.md](README.md) is the user-facing guide, and [OVERVIEW.md](OVERVIEW.md) is the data-access statement shown in
Paseo's plugin listing. [PRODUCT.md](PRODUCT.md) and [DESIGN.md](DESIGN.md) cover voice and the design system.

## Hard rules

- The name is Follow-up everywhere: the npm package `paseo-follow-up`, the plugin id `follow-up` and
  `plugin-data/follow-up`. 1.x ran under an older internal name; only `shared/legacy.ts` (and CHANGELOG.md) may spell
  it, to recognise and clean up what 1.x left behind. `tests/no-legacy-name.test.ts` enforces this and
  `scripts/rename-legacy-name.mjs` fixes the mechanical cases. Keep the `follow.*` RPC names and the `follow_*` tool
  names. Never reset tracked work or settings during an upgrade; 2.0 moves 1.x's data and plugin id once
  ([docs/updates.md](docs/updates.md#moving-from-1x)).
- Never commit credentials, daemon state, transcripts or local machine paths. Follow-up is public: prompts, prefixes, tool text and UI copy say "the developer" (they/their), never a person's name (tests/no-personal-names.test.ts). Where old text is matched, such as the Overseer's forward prefix, keep recognising the legacy spelling.
- Boolean settings use positive `enable_` names.
- Subprocesses take argument arrays, never a shell.
- Minimum Paseo is 0.15.0 (`requirements.paseo`). Agent tools are native; the stdio bridge stays as the fallback for hosts
  that serve no plugin tools (the agent MCP turned off).
- Use native React Native controls and host theme tokens.
- `server/mcp-source.ts`, `server/hook-source.ts`, `server/overseer-prompt-source.ts`, `server/wait-runner-source.ts`
  and `server/update-watchdog-source.ts` are generated by `scripts/build.mjs` (`npm run prepare`) from
  `server/mcp.mjs`, `server/agent-hook.mjs`, `server/overseer-prompt.md`, `server/wait-runner.sh` and
  `server/update-watchdog.mjs`. Commit the generated output with its source. They hold one line per source line, so a
  merge conflict in one mirrors its source: resolve the source, then rerun `node scripts/build.mjs`
  (`tests/generated-sources.test.ts` checks both).
- Never restart the developer's daemon or send test messages into real conversations. Tests use isolated Paseo and
  provider homes with synthetic agents ([docs/testing.md](docs/testing.md)).
- Every script that starts a Paseo daemon or a browser calls `await harness()` (`scripts/harness.mjs`) first, a
  machine-wide slot shared with the `harness-slot` wrapper, and starts daemons with `spawnDaemon` so none outlives it
  ([docs/testing.md](docs/testing.md#rules-for-harness-daemons)).

## Architecture map

```
Paseo app (web, desktop, phone)          Paseo daemon (host)                          Agent sessions (Claude Code, Codex)
  index.client.tsx                         index.server.ts: the plugin worker            native tools: mcp__paseo__follow_<name>,
  client/*.tsx: Home, panel, pill,   RPC     one process, owns plugin-data/follow-up   wait_* (served by Paseo's MCP, run in the worker)
  settings, brief card, chat rows   ────▶   handlers keyed by shared/contracts.ts   ◀──  stdio bridge: server/mcp.mjs (fallback when no host tools,
  shared/*.ts: pure logic, schemas         server/*.ts: engine, inbox, stores...          also a CLI: node "$FOLLOW_UP_CLI" call …)
                                           lifecycle hooks: server.on / server.before   provider hooks: server/agent-hook.mjs
                                                                                         wait runner: plugin-data/.../wait/run-job.sh
```

- **Client** (`index.client.tsx`, `client/`): registers Paseo surfaces (Home screen, larger view, workspace panel,
  settings screen, header button, sidebar item, composer pill, Command Center items, the `/follow-up` slash command,
  chat timeline renderers). It reads and writes only through RPCs. Map: [docs/client.md](docs/client.md).
- **Shared** (`shared/`): zod schemas, RPC contracts and pure logic (grouping, precedence, copy). Both sides import
  it, and most tests target it.
- **Server** (`index.server.ts`, `server/`): one worker per daemon. `contribute()` builds the stores and services,
  registers every RPC handler through `handle()` (which also keeps an in-process map so native tools run the same
  handler), subscribes to lifecycle events, and attaches tools to sessions at `agent.session_open`.
- **RPC contracts** (`shared/contracts.ts`): every client↔server and agent↔server call, as `defineRpc` contracts
  named `follow.<name>`. All of them are listed in [docs/rpcs-and-tools.md](docs/rpcs-and-tools.md).
- **Agent tools**: tool tuples live in `server/mcp.mjs` (`tools`, `actionTools`, `overseerTools`). At
  `agent.session_open`, `withTools` in `index.server.ts` attaches them natively (`server/native-tools.ts`), or
  falls back to the per-launch stdio bridge (`server/session-mcp.ts`). Which session gets which tools:
  [docs/rpcs-and-tools.md](docs/rpcs-and-tools.md). How native serving works: [docs/native-agent-tools.md](docs/native-agent-tools.md).
- **Provider hooks**: `server/agent-hooks.ts` installs `agent-hook.mjs` into Claude Code's `settings.json` and Codex's
  `hooks.json` for SessionStart, UserPromptSubmit, PostToolUse and Stop. It's gated by the `hooks-enabled.json` lease,
  which the worker renews. The hook adds context, nudges sync and `needs_you`, and adds Wait's guidance:
  [docs/hooks.md](docs/hooks.md).
- **Data**: everything lives in `$PASEO_HOME/plugin-data/follow-up/`. Each file is listed in
  [docs/data-files.md](docs/data-files.md).

## Invariants

These are product rules. Each has tests, and breaking one is a bug even when the tests pass.

1. **Never wake a dormant agent.** Reading an unloaded agent's timeline or provider subagents loads it (about 650 MB)
   for an hour. Check `isLoaded()` (`shared/agent-load.ts`) or use the cached directory first. For an unloaded
   agent, read its transcript on disk (`server/transcript.ts`). Auto-send skips agents that aren't loaded or that
   had no user message within the active window. Guarded by `tests/never-wake.test.ts`,
   `tests/daemon-load.test.ts` and `npm run test:scale`. See [docs/resources.md](docs/resources.md).
2. **Stay inside resource budgets.**
   - One worker process, and no process per agent or per job.
   - No polling while the app is hidden.
   - Background work (scans, auto-sends, AI jobs) waits while the governor reports the VM constrained
     (Paseo's cgroup working set ≥ 75 %, or pressure).
   - Extras stop at critical (≥ 85 %).
   - `test:scale` budgets (the gate in `verify`), on the realistic seed (`--realistic`: 140 workspaces, ~280 agents,
     three PRs with full snapshots per workspace, a fake GitHub with live-sized PR bodies): **300 MB peak RSS** from the
     worker's start (VmHWM, so the cold-start tick counts), **240 MB idle RSS** (the median of the idle window), **3 %
     idle CPU**, **2 idle daemon requests a minute**. Measured 2026-11-12 (two runs): peak 262–264 MB (a ~2 s cold-start
     tick that changes and validates every workspace once), idle 198–200 MB and flat, CPU 1.3–1.4 %, 1.3 requests a
     minute; the bare plugin process is ~120 MB. Headroom (~15 % peak, ~20 % idle) covers live's extras the seed lacks
     (archived agents, real transcripts, AI jobs) and CI noise. The old 240 MB budget was checked on an empty-workspace
     seed and only after start-up, so a 450 MB live worker passed it.
   - `test:scale:live` (PR CI, after `verify`): the same budgets on the **live-sized** seed (`--live-sized`: plus one
     153-PR workspace and a live-shaped 120 KB inbox) after a 180 s **busy window** (awake agents end 20 turns a minute
     with live-sized timelines), plus **busy-window growth** under `BUSY_GROWTH_BUDGET_MB` (`scripts/scale-budget.mjs`).
     It runs with `--budgets-report-only` (budgets print as `[report]` lines; dormant wakes and unsettled sends still
     fail) until its derived budgets land: 2026-11-13 the busy window sat at 322–352 MB idle on beta.4, main and the
     memory fix alike, ~100 MB JS heap and ~220 MB native. Never loosen a `test:scale` budget to pass it.
   - **Budgets judge the typical cost** (`scale-budgets-judge-the-typical-cost`): an idle budget reads the idle window's
     median, because RSS there is a GC sawtooth (main swung 17 MB between runs; CI once peaked at 279 MB over a ~215 MB
     median). One sample decides nothing except the lifetime cap (VmHWM ≤ 300 MB). The idle peak is still reported.
     The send phase's bound comes from the worker's send schedule (`SETTLE_MS`, `POLL_IDLE_MS`, `NO_PROGRESS_CAP`) plus
     a named margin, timed from the worker loading the seed, never a literal that equals a normal run's length.
     Guarded by `tests/scale-budget.test.ts`.
   - **A tick copies the state at most once** (`a-tick-copies-the-state-at-most-once`): per-workspace writes copy one
     workspace, a tick saves and runs `onChanged` once (`Store.batch`), an untouched workspace isn't copied or
     re-checked, and a save validates only changed workspaces. Per-tick work never scales with workspaces × agents.
     See [docs/architecture.md](docs/architecture.md); guarded by `tests/tick-copies.test.ts` and `test:scale`.
   - **A send never clones the whole state** (`a-send-never-clones-the-whole-state`): a send, its acknowledgment, an
     answer's delivery and every agent turn event write only the workspace they are about (`mutateWorkspace`,
     `server/turn-events.ts`), never walking all of them, and a whole-state `mutate` keeps unchanged workspaces'
     objects so a save validates only what changed. Guarded by `tests/send-clones.test.ts` and `test:scale`.
   - **A mutation copies only what it changes** (`a-mutation-copies-only-what-it-changes`, which generalises
     `a-send-never-clones-the-whole-state` to every store): a store's mutation works on a copy-on-access draft
     (`server/cow.ts`): reading copies nothing, an item is copied only on its first real write, and **a write that
     changes nothing isn't a write** (setting a field to the value it has, or deleting one that isn't there: no copy,
     no stringify, no zod, no flush). Unchanged items keep their frozen objects, only what changed is validated, and
     the store serialises once per real write. Every JSON writer in `server/` uses it or carries an exemption with a
     reason. Guarded by `tests/inbox-copies.test.ts`, `tests/store-copies.test.ts`, `tests/discovery-noop.test.ts`
     (a discovery tick that finds nothing new copies nothing) and `test:scale`'s busy window.
   - **A timeline entry is read once** (`a-rescan-reads-only-new-entries`, `a-turn-end-reads-the-turn-once`): a running
     agent's rescan reads forward from its cached cursor (`direction: "after"`), never a fixed newest page, and a turn
     end reads its own turn (back to the item that started it, at most `TURN_READ_CAP`) once, shared by the engine and
     the inbox (`turnItems`, `server/inbox-directory.ts`). Guarded by `tests/incremental.test.ts`,
     `tests/turn-read.test.ts` and `test:scale`'s busy window.
   - **A running worker holds one daemon connection** (`a-running-worker-holds-one-daemon-connection`): the shared
     connection's idle close is the engine's tick plus a named margin, so ticks reuse it. Guarded by
     `tests/daemon-connection.test.ts`.
   - **A send lists agents at most once per tick** (`a-send-lists-agents-at-most-once-per-tick`): sends read the tick's
     agent list (patched by events); no `fetch_agents` or `fetch_agent` per send or per turn event, and subagents at
     most once per agent per tick. Guarded by `tests/daemon-load.test.ts` and `test:scale`
     ([docs/architecture.md](docs/architecture.md)).
   - **A check costs linear in its workspace** (`a-check-costs-linear-in-its-workspace`): one status check (and every
     surface it builds) tokenizes each question once (`featuresOf` in `shared/questions.ts`, cached per question and
     checked against its text) and orders a stack with one depth pass (`depths` in `shared/attention.ts`), never a
     pairwise re-tokenize or a parent `find` inside a sort. 2026-11-13: one check of a 153-PR, 52-question workspace
     allocated 3.9 MB in ~11 ms; now 1.55 MB in 3–6 ms. Guarded by `tests/check-linear.test.ts` (200 questions,
     300 PRs).
3. **Agent parity.** Every action the developer can take in Follow-up also has an agent tool that runs the same
   server path, or an exemption with a reason in `PARITY` (`server/agent-parity.ts`).
   - Writes return a dry-run plan first and run with `confirm: true` and the plan id.
   - Agent writes go into the inbox ledger as `agent:<id>`.
   - `tests/agent-parity.test.ts` reads the client's RPC imports and fails on a new RPC without an entry.
   - There are no human-only actions. Follow-up also has no button for archiving, untracking a workspace or
     putting one on hold, so there's no tool for those either.
4. **Agents act on others, not themselves.** An agent can't sign itself off, answer its own question through
   `answer_question`, or act on its own brief. Goal, tasks, questions and Done belong to the main agent.
   Contributors get `workspace_status`, `register_pr`, `sync_workspace` and `make_main_agent` (under its claim
   rules), plus `report_issue` (it changes nothing in Follow-up), and nothing else.
5. **Ownership comes from the daemon.** The caller is `context.agent.id` (native tools) or `PASEO_AGENT_ID` checked
   by the daemon (bridge), never a tool argument. Unknown parent membership grants no new scope.
6. **Nothing irreversible on its own.**
   - Follow-up never merges, turns on merge-when-ready, requests reviewers or archives by itself. The developer's
     Merge is one click that names its whole scope first and merges exactly that at the heads it showed
     (`a-click-on-merge-merges`, `shared/merge-click.ts`); agent tools still dry-run, then run with `confirm: true`.
   - Completion checks never auto-send.
   - Answers go out only on the developer's Send.
7. **Unknown is not off.** An unreadable toggle or setting means the default, never "off". A seen user message
   from no known sender counts as the developer's, which clears a flag rather than adding one. A turn whose prompt
   wasn't seen is `unknown`, and only the developer (`tom`) may answer a brief.
8. **Design through `/impeccable`.** Every UI change goes through `/impeccable critique`, and you render every
   state yourself: desktop and 390×844, light and dark, no horizontal overflow. DESIGN.md and PRODUCT.md set the
   system and voice. User-facing copy calls the `about` feature "Summary". A 44px bar holds icons only: chips and counts go on
   their own wrapping line, so nothing pushes settings off-screen at 390pt. Never offer an action the server will
   refuse (an Add row at a cap): refuse up front with the reason. Search never fuzzes numbers: ids match exactly
   or by prefix.
9. **No root treatment for background agents.** A Paseo 0.16 `background: true` agent is another plugin's helper.
   Follow-up gives it no tools, no Wait, no `needs_you` or Stop-hook nudge, no inbox rows and no directory row
   (`server/background-agents.ts`, `tests/background-agents.test.ts`). On 0.15 the field is absent.
10. **Stopping never waits on stuck work** (`worker-stop-never-waits-on-a-stuck-pass`): stop finishes within one
   deadline, and work that ends inside it is kept. The worker's stop clears its timers, so a wait with no bound on work
   stuck on the daemon, Paseo or a CLI that never answers leaves stop pending for good (a reload waits on the old
   worker). `stopWorker` (`server/teardown.ts`) gives the whole stop one deadline (`STOP_WAIT_MS`, from when stop
   starts) and every wait what is left of it: start-up, hooks, `PrActions.close`, `closeConnections`, `Engine.stop` and
   the store's queue; bounds per wait added up to about 45 s. `Store.close` refuses new mutations at once, commits one
   already accepted if it finishes inside the deadline, and drops (with the "stopping" error, writing nothing) one that
   finishes after it. Guarded by `tests/worker-stop.test.ts`.
11. **Reporting an issue costs no standing context and posts nothing without a yes**
   (`report-issue-costs-no-standing-context`, `report-issue-files-only-after-confirm`,
   `report-issue-never-carries-secrets`). `report_issue`'s description is one line of at most 150 chars; its procedure
   comes back from the first call, and nothing is added to hooks or instructions. The dry run only reads; filing needs
   `confirm` with the plan id (and `screenshot_consent` when there are screenshots). Everything an issue carries goes
   through one Redactor. Guarded by `tests/report-issue.test.ts` and `tests/report-issue-redact.test.ts`
   ([docs/report-issue.md](docs/report-issue.md)).
12. **A rename is always undoable and never wakes an agent** (`rename-is-always-undoable`,
   `rename-never-wakes-an-agent`). Rename with AI renames only on the developer's Rename (or an agent's confirmed
   `ai_rename`), records the title it replaced, and Undo restores that exact title for 24 h unless the workspace was
   renamed again since. Its suggestion reads stored data only, and its daemon calls are `fetch_workspaces` for one id
   and `set_workspace_title`. Guarded by `tests/rename.test.ts` ([docs/ai-roles.md](docs/ai-roles.md#rename-with-ai)).
13. **Every list row has the row menu** (`every-list-row-has-the-row-menu`). `menu` is required on `HomeList` and its
   rows' opener is required, so right-click, long-press and Shift+F10 open Follow-up's row menu on every list (Home,
   search results, the sidebar view), never the platform's Copy/Paste menu. Items a surface can't serve are left
   out, not shown dead. Guarded by `tests/row-menu.test.ts` ([docs/client.md](docs/client.md#row-menu)).
14. **Menu glyphs centre on their item** (`menu-glyphs-center-on-their-item`). Every menu item (the sort menu, the row
   menu, the panel's More menu) lays out through `MenuItemContent` (`client/menu-item.tsx`): one leading glyph slot
   centred on the item, sized for touch as its text is. No menu builds its own glyph slot, and none pins a glyph to
   the first line. Guarded by `tests/menu-glyph.test.ts` ([docs/client.md](docs/client.md#row-menu)).
15. **A search result is the list's own Row** (`search-row-is-the-list-row`). Home's search results render the same
   `Row` as Home's groups (`client/home-list.tsx`), with the hit highlighted in place (title, "› agent", the ask line);
   a match in a field the row doesn't show replaces line 2 with "<Field> · excerpt", so a result is exactly as tall as
   its row. An archived hit is that Row, muted, with the Archive glyph and "Archived". The sidebar view's "Filter
   workspaces" narrows its list in place with the same matcher (`filterHome` in `shared/search.ts`,
   `sidebar-filter-uses-home-search`). Home's order is one Display setting, `home_sort`, for Home and the sidebar view
   on every device, so `set_display` covers it. Guarded by `tests/search-row.test.ts`, `tests/home-beta2.test.ts` and
   `tests/home-sort.test.ts`.
16. **Auto-send says the truth and keeps moving** (`the-send-line-matches-the-send-decision`,
   `message-rows-say-it-once`, `a-capped-task-never-holds-the-queue`). One pure `sendDecision`
   (`shared/send-decision.ts`) decides an auto-send and writes every line about it; the engine sends exactly when it
   says send. Repairs are tasks: a row in the next message says only Queued or Sent, and the Tasks strip carries when
   and why. A turn without an acknowledgment never blocks; only a condition sent twice unchanged, acknowledged or not,
   waits, as its own task. Guarded by `tests/send-decision.test.ts`, `tests/no-retry.test.ts` and `tests/task-rows.test.ts`
   ([docs/workspaces.md](docs/workspaces.md#repairs-are-tasks-q49)).
17. **A No review repository never asks for review or merge** (`a-no-review-repo-never-asks-for-review-or-merge`).
   A repository is Team review (the default: the developer adds reviewers and merges) or No review (the agent merges
   its own PRs once checks pass), set in Settings → PR workflow or with `set_pr_workflow review`. One rule decides it:
   `agentMerges(pr)` in `shared/pr-workflow.ts` is the PR's own register_pr answer, else whether its repository is No
   review. Every consumer (the reviewers ask, merge asks, the quiet merge, status invariants) reads that helper, never
   `pr.agentMerges`; the set of No review repositories is filled before the first tick and on every save, so the
   lookup costs a set read. Guarded by `tests/review-mode.test.ts` ([docs/prs.md](docs/prs.md#review-mode)).
18. **An idle open client makes at most one RPC a minute** (`idle-client-makes-at-most-one-rpc-a-minute`). On Paseo
   0.16 the client subscribes to the worker's feeds (`follow.workspaces-feed`, `follow.inbox-feed`, `follow.home-feed`,
   `follow.display-feed`) instead of polling. The worker serves each topic once, from state it already holds, and
   pushes only a value that changed: no polling on the server and no per-subscriber timers (`server/feeds.ts`). On
   0.15 (no `client.subscribe`) the client polls as before. Quiet must not mean stale: a feed the worker closes (a
   restart) or refuses polls until it resubscribes and stays subscribed, and a feed that keeps dropping backs off
   instead of looping (`openFeed`, `client/feeds.ts`). Guarded by `tests/idle-rpc.test.ts`
   (ten simulated minutes of the real stores, on both hosts), `tests/feed-recovery.test.ts`, `tests/feeds.test.ts`
   and `npm run test:feeds` (the harness, end to end) ([docs/client.md](docs/client.md#feeds)).
19. **The recovery agent is quiet, keeps its tools and unloads** (`recovery-is-quiet-keeps-its-tools-and-unloads`).
   On a host with `features.backgroundAgents` (Paseo 0.16) it is created `background: true` (no tab, no ping, no
   sidebar row); never on 0.15, whose path is unchanged. Invariant 9's background skip exempts only the agent
   Follow-up's own record names as a recovery recipient, never one carrying recovery labels. The same record lets it
   through every "root agents only" gate it needs (`mayEnroll` for `enroll_workspace`). "Unloads" means
   host-collectable: no plugin API closes an agent by id, so a settled batch (acknowledged or failed) leaves no running
   turn, pending permission or background work, and Paseo's idle-runtime cleanup releases it. Guarded by
   `tests/recovery-background.test.ts` and `scripts/check-recovery-background.mjs`
   ([docs/workspaces.md](docs/workspaces.md)).
20. **An answer leaves Needs you only when delivered** (`an-answer-leaves-needs-you-only-when-delivered`,
   `put-in-chat-never-rewrites-a-draft`). Copy and Put in chat (Paseo 0.16) record the developer's answer but send
   nothing, so it stays in Needs you as "Your Qn answer isn't sent yet" until a turn of that agent ends with
   `Follow-up answer Qn (` in its user messages (the bounded tail `turn_ended` already reads; no new reads), Send
   delivers it (the row's Send sends the recorded pick and note in one click), or Sign off on that agent's row settles
   it. Put in chat never calls `setPrompt`: it focuses the agent's composer at the end of the draft and inserts the
   answer (after a blank line when there's a draft), does nothing when the exact answer is already there, and falls
   back to Copy when the composer can't come on screen (`putInChat`, `shared/put-in-chat.ts`). Guarded by
   `tests/answer-delivery.test.ts`, `tests/put-in-chat.test.ts` and `INVARIANTS` ([docs/needs-you.md](docs/needs-you.md#answers-waiting-to-be-sent)).
21. **A brief without an ask never sits beside Needs you** (`a-brief-without-an-ask-never-sits-beside-needs-you`).
   "No ask stated" or a done brief's "Nothing needed" is drawn only while nothing in Needs you speaks for the row;
   beside a question or an answer waiting to be sent it would say there's nothing to do. One predicate decides it,
   `briefCardShown` in `shared/brief.ts`. Guarded by `tests/brief-card.test.ts`.
22. **View state is per device; settings are per host** (`view-state-is-per-device-settings-are-per-host`). The
   settings category, settings folds, Home group folds and What's new "seen" live in the device settings document
   `follow-up-view` on Paseo 0.16 (`client/view-store.ts`), with localStorage kept as the first-paint cache for one
   release; on 0.15 they stay in localStorage. Anything an agent can set stays host-scoped, so the worker and its
   tools reach it: `home_sort` is a Display field, never device-scoped. Reads paint the cache first and the document
   when it loads, never the default in between. Needs you opens on every mount. Guarded by
   `tests/view-settings.test.ts` (including the `home_sort` host-scope scan) and `scripts/check-view-settings.mjs`
   ([docs/settings.md](docs/settings.md)).
23. **A row that names a PR opens it in one click** (`a-row-that-names-a-pr-opens-it-in-one-click`). Every Needs-you
   item about one PR carries `pr` (`prLink` in `shared/presentation.ts`: Graphite when the PR ships through Graphite,
   else GitHub, the PR sheet's rule), and its row draws that link beside its action, never instead of it. Every "#N"
   that a Needs-you row, a brief or Home's Recent steps name, and the workspace tracks, links that PR (`PrLinksProvider`,
   `client/rich-text.tsx`); a brief about a PR has Open PR; `inbox_list` gives agents each row's PR urls. Guarded by
   `tests/pr-open-link.test.ts` and `INVARIANTS`.

## Bugs

Every bug is fixed for its whole class:

1. Find the root cause.
2. Write a test that fails on main.
3. Fix it at the source.
4. Add an invariant to `INVARIANTS` in `shared/status-invariants.ts`. `tests/status-invariants.test.ts` runs every
   invariant over a grid of workspaces, plus one fixture per reported bug. Each invariant's `id` names the bug class
   it guards (e.g. `no-duplicate-open-question`), and its `check` is pure and never throws.

Status bugs (two surfaces disagreeing, a label that isn't true) come from computing a status inline. Every
user-facing status (Home bucket, header live line, agent card, batch line, Needs you, pills) derives from
`shared/status.ts`. The worker logs contradictions it meets at runtime to
`plugin-data/follow-up/status-diagnostics.jsonl` (`server/status-check.ts`); read it when a status looks wrong.

## How to test

Run these before every PR: `npm run verify`, `npm run test:install` and `npm pack --dry-run`. What each covers,
the extra scripts, and how to start an isolated preview daemon (`npm run preview`) are in
[docs/testing.md](docs/testing.md). Rules for harness daemons (any isolated daemon a script starts):

- Before starting one, check the host's Paseo working set: `memory.current` minus `inactive_file` from
  `/sys/fs/cgroup/system.slice/paseo.service/` must be under 75 % of the service's memory limit. This is a coarse
  manual check. The governor's own measure, which also subtracts `slab_reclaimable`, is in
  [docs/resources.md](docs/resources.md).
- Run one harness daemon at a time, and stop it when you're done.
- Synthetic data only. Never point a check at `~/.paseo`, the live daemon or a live plugin install.
- Run large scans inside a memory-capped scope (`systemd-run --user --scope -p MemoryMax=4G …`) so page cache isn't
  charged to Paseo.

## How releases work

See [docs/releasing.md](docs/releasing.md). In short:

- **A release needs Tom's manual permission, every time.** No agent releases on its own. Features and fixes ship to a
  beta by default (`X.Y.Z-beta.N`, npm `beta` dist-tag). Anything else needs Tom's explicit OK for that exact version
  before it's tagged: an rc (`2.0.0-rc.0`), a stable version, npm `latest`, or a hotfix (a hotfix skips the beta, not
  the permission). Ask him, and quote his OK in the release commit body.
- A PR that changes something users see adds `changes/<branch>.md` (rules in `changes/README.md`).
- The orchestrator (Tom, or the coordinating agent he runs releases from), not the feature PR, runs
  `npm run release:notes <version>`, then bumps the version in the same release commit, tags `vX.Y.Z`, and lets the
  npm workflow publish. Versions with a prerelease part (`1.4.0-beta.24`) publish under the `beta` dist-tag.
  Betas get no CHANGELOG section; a stable or a major's rc gets a CURATED one (release:notes writes a draft that
  check:notes refuses until it's rewritten). A major's rc (`2.0.0-rc.0`) carries the major's section, `## 2.0.0`.
- Every GitHub release has notes in one format (`scripts/release-body.mjs`): a beta's page renders the fragments
  added since the previous tag, a stable's or an rc's its curated section. In-app What's new stays major-only.
- Don't bump the version in a feature PR.

## Common pitfalls

- **A plugin reload detaches native tools.** Every `paseo plugin reload` or update drops the `follow_*` and
  `wait_*` tools from open sessions until each session reopens (before its next prompt). Mid-turn calls fail with
  "Tool not found". The hook tells the agent to use the bridge (`tools-instance.json` vs
  `hook-state/native-<agent>.json`). Don't "fix" a missing tool by reinstalling in a loop.
- **Timeline transforms must not break Paseo's grouping.** A transformed tool call leaves Paseo's tool group and
  renders loose. Keep routine tools untransformed. Paseo's `create_agent` / `create_workspace` calls are replaced by
  Follow-up's created card, so the group's "N tool calls" count excludes them, like the Done card. Rules: [docs/client.md](docs/client.md#chat-rows-and-paseos-grouping),
  guarded by `tests/chat-grouping.test.ts`.
- **Native tools have no MCP `instructions`.** Guidance for native tools goes through tool descriptions and the
  SessionStart hook (`server/agent-hook.mjs`), not through the bridge's `initialize` reply.
- **Forgetting `npm run prepare`.** Editing `server/mcp.mjs`, `server/agent-hook.mjs`, `server/overseer-prompt.md`
  or `server/wait-runner.sh` without regenerating means the packed plugin ships the old copy.
- **Adding a tool in one place.** A new agent tool needs:
  - its tuple in `server/mcp.mjs`;
  - its handler in `server/agent-actions.ts` (or an `RPC_TOOLS` entry in `server/agent-parity.ts`);
  - a `PARITY` entry, if it mirrors a client RPC;
  - the tool count in `tests/mcp-usage.test.ts`;
  - its classification in `TOOL_PRESENTATION` (`shared/chat.ts`): routine unless the developer must see that moment
    (see [docs/client.md](docs/client.md#chat-rows-and-paseos-grouping));
  - a mention in [docs/rpcs-and-tools.md](docs/rpcs-and-tools.md).
- **Adding an RPC without parity.** A client-called RPC needs a `PARITY` entry (tool or exemption) and a line in
  [docs/rpcs-and-tools.md](docs/rpcs-and-tools.md).
- **Reading `state.json` from hooks or the bridge.** They run on every tool call. Read `scopes.json` (a few KB),
  which the worker writes on change.
- **Trusting Paseo's `updatedAt`.** The daemon rewrites it in bulk. Activity is the unread time or the developer's
  last message.
- **Timeline reads on agent events.** `agent.turn_ended` can read a bounded tail (the agent is live). Anything
  outside a live event must check `isLoaded()` first.
- **CI doesn't run everything.** It runs no live-model check.
  - PR CI (`.github/workflows/ci.yml`) runs the publish workflow's gate: `verify`, `test:install` and
    `npm pack --dry-run`, with Paseo 0.15.2 and the same Claude and Codex CLIs. `tests/publish-gate.test.ts`
    (invariant `publish-gate-checks-run-on-every-pr`) fails when the publish workflow runs a check PR CI doesn't.
  - Neither has model credentials, so `check-wait` skips there.
  - When you touch Wait, run `npm run test:wait-live` locally.
